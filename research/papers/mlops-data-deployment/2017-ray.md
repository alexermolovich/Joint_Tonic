## Core paper explanation

The Ray paper describes distributed execution with stateless tasks, stateful actors, a distributed object store, and lineage-based recovery. These primitives support dynamic reinforcement-learning and simulation workloads whose dependency graphs evolve at runtime.

## Execution flow

### Build task dependencies

A task $y=f(x_1,\ldots,x_n)$ can run once its input objects are available. The dependency graph is a DAG for ordinary tasks; actor methods additionally interact with mutable actor state. This is a systems interface, not a machine-learning objective.

### Schedule and move data

A teaching lower bound on elapsed time is
$$T\ge\max(T_{\mathrm{critical\ path}},W/P),$$
where $W$ is total compute work and $P$ effective parallel capacity. Communication, serialization, scheduling, and heterogeneous resources add overhead. This bound is explanatory, not Ray's scheduling algorithm.

### Recover and trace execution

Pure deterministic task replay can reconstruct lost derived objects from dependencies. External side effects and stateful actors require additional semantics; retrying a task does not automatically give exactly-once physical actions. Keep dataset IDs, seeds, and policy versions attached to distributed robot rollouts.

## Why this matters on a robot

Distributed execution can accelerate simulation and dataset processing. Duplicate side effects, nondeterministic retries, and oversized object transfers can damage reproducibility or throughput; robot commands should not be treated as replayable pure tasks.
